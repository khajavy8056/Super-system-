# ADR — Architecture Decision Records

ثبت تصمیم‌های معماری (پذیرفته‌شده توسط مالک پروژه در 2026-09-04).

---

## ADR-001 — منبع حقیقت قیمت فروش: PriceVersion محور ✅
**وضعیت:** پذیرفته‌شده (گزینه A)

- `PriceVersion` منبع حقیقتِ «قیمت استراتژیک» کالاست (تاریخچه نسخه‌بندی‌شده و تغییرناپذیر).
- هر `ProductBatch` در لحظه ورود، قیمت فروش خود را از نسخه فعال ارث می‌برد و آن را **ثبت (snapshot)** می‌کند — به همین دلیل «قیمت قدیم/جدید» هم‌زمان قابل فروش می‌ماند (الزام §16).
- تغییر قیمت از پنل = نسخه جدید + اثر بر Batchهای آینده (Batchهای موجود دست نمی‌خورند، مگر با تصمیم صریح کاربر).
- فروش همیشه از قیمت Batch می‌فروشد؛ اگر Batch قیمتی نداشت → fallback به نسخه فعال.
- `receive_batch` اولین Batch اگر نسخه فعالی وجود نداشت → نسخه فعال اولیه می‌سازد (تاریخچه از روز اول پر می‌شود).

## ADR-002 — معماری موبایل: PWA ✅
**وضعیت:** پذیرفته‌شده

- اپ موبایل به‌صورت **PWA** (manifest + service worker) از همان codebase پنل وب.
- اسکن بارکد با دوربین: `BarcodeDetector` API + fallback کتابخانه JS (ZXing) در مرورگرهای بدون پشتیبانی.
- آفلاین: IndexedDB + صف محلی + Sync با Conflict detection (تا وقتی تست واقعی نشود، ادعای «کار می‌کند» ثبت نمی‌شود).
- نصب روی اندروید: Add to Home Screen / TWA در فاز بعدی بررسی می‌شود. APK بومی ساخته نمی‌شود.

## ADR-003 — استقرار نسخه اول: تک‌ماشینه SQLite ✅
**وضعیت:** پذیرفته‌شده

- v1 برای یک صندوق/یک فروشگاه: SQLite (WAL) روی همان دستگاه — آفلاین کامل، بدون هزینه سرور.
- تمام کوئری‌ها با SQLAlchemy 2.0 نوشته می‌شوند تا مهاجرت بعدی به PostgreSQL (LAN/چندترمینال) فقط تغییر `DATABASE_URL` + تست باشد.
- کاهش اتمیک موجودی (`UPDATE … WHERE current_qty >= n`) از همین فاز اعمال می‌شود تا در استقرار چندکاربره، semantics درست باشد.

## ADR-004 — Providerهای خارجی بارکد: افزونه‌ای
**وضعیت:** پیشنهادی (فاز ۱ نهایی می‌شود)

- معماری `Provider` interface + Registry؛ هسته سیستم به هیچ Provider خاصی وابسته نیست.
- پیش‌فرض تست‌پذیر عمومی: OpenFoodFacts (رایگان، بدون کلید). GS1 و Providerهای ایرانی به‌صورت افزونه با API key از تنظیمات.
